**Result: the alteration was detected at exactly the altered entry.** Once Org1's peer served the
altered value (row 5), `VerifyLogChainIntegrity` on that peer reported the chain broken at
`req-20261015T083729-1001` (row 7), because the stored `hash` no longer matched the hash
recomputed from the entry's fields. Org2's peer keeps its own copy of the world state. It still
held the true `GRANTED` entry and reported the chain intact (rows 6 and 8), so the two
organizations' copies disagreed, which exposes the tampering a second way, independently of the
hash chain. After the original document was restored, both peers again reported the chain intact
(rows 10 and 11). The test added no blocks (the channel height stayed at 42), because queries and
direct database edits never pass through ordering.

### 6.2 Observation: the peer's state cache

A first attempt made the same edit without restarting peer0.org1. Immediately afterwards, the
peer still returned the original entry and reported the chain intact:

```
GetLogEntry on peer0.org1:             {"requestId":"req-20261015T083729-1001","outcome":"GRANTED","loggedAt":"2026-10-15T08:37:48.13793942Z","seq":7,"prevHash":"9786e437852120174df087680fb868a30d671f8d722cb23cbce108ef6a153590","hash":"116ac464665daa3fcef015e814278743bba8de83274f7fcf9817efe62f9720e6"}
VerifyLogChainIntegrity on peer0.org1: {"intact":true,"brokenAt":""}
```

This happens because a Fabric peer keeps a cache of world state in memory in front of CouchDB.
The edit bypassed the peer, so the cache was not updated. The altered value reaches the
chaincode once the cached entry is dropped, either when the peer restarts (as in 6.1) or when the
cache evicts it. The edit was reverted before the second attempt. This does not weaken the
result: the tampering went undetected only while the peer was still serving the original, correct
value, and it was detected as soon as the altered value was served.

## 7. What this evidence does and does not cover

This demonstrates the chaincode running inside real Hyperledger Fabric peers on a
two-organization network. Every state change was endorsed by both organizations, ordered by the
Raft orderer and committed to both peers' ledgers. The access decisions (GRANTED, then DENIED
after revocation), the hash-chained audit log and the error handling behave exactly as in the
in-memory run in `test_evidence.md`, and the tamper-evidence property holds on the live ledger.

It does **not** cover:

- **Per-user identities.** The API signs every transaction as the Org1 Admin. A real deployment would issue Fabric CA identities to individual patients and providers.
- **Atomic verify-and-log.** `VerifyAndGrantAccess` and `LogAccessEvent` are separate transactions (blocks 36/37 and 40/41), so a failure between them would leave a decision without a log entry.
- **Concurrent logging.** Every `LogAccessEvent` updates a single chain-head key, so two log writes in the same block would conflict and one would be rejected. The run above was sequential.
- **Choice of entries to check.** `VerifyLogChainIntegrity` checks the request IDs it is given, in the order given. Here the order was read from the ledger by sequence number.
- **The usability evaluation (Section 4.8, step (d)),** which needs the web application and participants.
